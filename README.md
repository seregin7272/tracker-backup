# Tracker Backup

Бекап Яндекс Трекера: задачи со всеми полями, комментарии, история изменений, связи и вложения,
плюс метаданные — описания глобальных и локальных полей, настройки очередей, справочники.

## Что сохраняется

Бекап лежит в одной папке (`--out`). Внутри три уровня: общие файлы прогона, справочники
организации и папка на каждую очередь, где у каждой задачи своя папка.

```
<out>/
├── queues.json          ← какие очереди выгружались в последнем прогоне
├── state.json           ← отметки для инкрементальных запусков (не пишется с --limit)
├── errors.json          ← ошибки последнего прогона, [] — всё чисто
├── _meta/               ← справочники всей организации
│   ├── fields.json        глобальные поля: id, название, тип, варианты значений
│   ├── statuses.json      статусы
│   └── priorities.json · issuetypes.json · resolutions.json · linktypes.json
└── <QUEUE>/
    ├── _queue/          ← настройки очереди
    │   ├── queue.json        очередь целиком: название, владелец, типы задач, воркфлоу
    │   └── localFields.json  локальные поля этой очереди
    └── <KEY>/           ← одна задача, например DEV-123
        ├── issue.json        сама задача со всеми полями
        ├── comments.json     комментарии
        ├── changelog.json    история изменений
        ├── links.json        связи с другими задачами
        ├── attachments.json  список вложений
        └── attachments/
            └── <id>_<name>   файлы вложений
```

### Что в файлах задачи

- **`issue.json`** — задача в том виде, в каком её отдаёт API: `key`, `summary`, `description`,
  `status`, `type`, `priority`, `assignee`, даты, `sla`, `followers` и так далее. Пустые поля API
  не присылает, поэтому набор ключей у задач разный.
  - Локальные поля очереди лежат здесь же, с ключами вида `<id>--<key>`, например
    `6920439eaa938f7498708bca--placementLocations`. Расшифровка такого ключа — в
    `<QUEUE>/_queue/localFields.json`.
- **`comments.json`** — список комментариев. У каждого есть `text` (разметка Трекера) и
  `textHtml`, автор, даты и `attachments` со ссылками на вложения комментария.
- **`changelog.json`** — история изменений: кто, когда и какое поле поменял, с `from` и `to`.
  Отдельно сохраняются сработавшие триггеры.
- **`links.json`** — связи с другими задачами, с типом связи («блокирует», «дубликат» и т.д.).
- **`attachments.json`** — все вложения задачи, включая прикреплённые к комментариям: у таких
  заполнено `commentId`. По каждому вложению хранятся `id`, `name`, `size`, `mimetype` и автор.
- **`attachments/`** — сами файлы. Имя файла — `id` из `attachments.json` и исходное имя;
  префикс нужен, чтобы два вложения с одинаковым именем не затёрли друг друга. Опасные символы
  в именах (`/`, `:` и подобные) заменяются на `_`. Папки нет, если вложений нет или запуск был
  с `--no-files`.

### Как связаны файлы между собой

| Что в задаче | Где расшифровка |
|---|---|
| ключи `<id>--<key>` в `issue.json` | `<QUEUE>/_queue/localFields.json` |
| `field.id` в `changelog.json`, глобальные поля | `_meta/fields.json` |
| `status`, `type`, `priority`, `resolution` | `_meta/statuses.json`, `issuetypes.json`, `priorities.json`, `resolutions.json` |
| тип связи в `links.json` | `_meta/linktypes.json` |
| `commentId` во вложении | `id` в `comments.json` |
| файл в `attachments/` | `id` и `name` в `attachments.json` |

### Как бекап обновляется

- При каждом запуске файлы задачи перезаписываются целиком: это всегда актуальный снимок
  задачи, а не накопление версий. Историю изменений даёт `changelog.json`.
- Уже скачанное вложение с тем же размером повторно не качается.
- Удалённые в Трекере вложения и задачи из бекапа не удаляются.
- Если задача переехала в другую очередь, она сохранится в папке новой очереди под новым ключом.
  Старая папка останется — её следует считать устаревшей копией. Старый ключ при этом есть
  в `aliases` в `issue.json` новой задачи.
- Каждый файл сначала пишется во временный (`*.tmp`, для вложений — `*.part`) и только потом
  переименовывается, поэтому при прерывании скрипта, в том числе по Ctrl+C или `docker stop`,
  готовые файлы не бывают полузаписанными, а временные удаляются. Принудительной записи на диск
  (`fsync`) нет: после внезапного отключения питания последние записанные файлы могут оказаться
  пустыми — в этом случае перезапустите прогон с `--full` для затронутых очередей.

## Запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

export TRACKER_ORG_ID=1234567          # Яндекс 360 -> X-Org-ID
# или TRACKER_CLOUD_ORG_ID=bpf...       # Cloud Organization -> X-Cloud-Org-ID

export TRACKER_TOKENS=y0_aaa,y0_bbb    # пул токенов
# или --tokens-file tokens.txt (по токену в строке, # — комментарий)
# или один токен: TRACKER_TOKEN=y0_...

.venv/bin/python tracker_backup.py --out ./backup                    # все очереди, инкрементально
.venv/bin/python tracker_backup.py --out ./backup --queues DEV,OPS
.venv/bin/python tracker_backup.py --out ./backup --full --no-files  # заново, без вложений
```

## Параметры запуска

### Аргументы командной строки

| Аргумент | По умолчанию | Описание |
|---|---|---|
| `--out DIR` | `./tracker-backup` | Каталог бекапа. Создаётся, если его нет. Повторные запуски пишут в тот же каталог и дополняют его. |
| `--queues A,B,C` | все очереди | Ключи очередей через запятую. Пробелы, пустые значения и повторы отбрасываются. Без параметра скрипт берёт список всех очередей организации, доступных токену. |
| `--full` | выкл. | Выгрузить выбранные очереди целиком, не глядя на `state.json`. Отметки очередей, не вошедших в прогон, не стираются. |
| `--no-files` | выкл. | Не скачивать вложения. `attachments.json` и сами файлы не создаются; прочие данные выгружаются как обычно. |
| `--limit N` | без лимита | Не больше N самых свежих задач (по `updated`) на очередь, N ≥ 1. `state.json` при этом не обновляется — режим для проверки на реальных данных. |
| `--tokens-file FILE` | — | Файл с токенами: по одному в строке, пустые строки и строки с `#` пропускаются. Объединяется с `TRACKER_TOKENS`, дубли убираются. |
| `--rps R` | `TRACKER_RPS` или 5 | Лимит запросов в секунду **на один токен**, дробные значения допустимы (`0.5` — запрос раз в 2 секунды). `0` — без лимита. |
| `--workers N` | 4 на токен, не больше 32 | Число параллельных потоков, которые качают комментарии, историю, связи и вложения. Скорость всё равно ограничена `--rps`, поэтому больше `--rps × число токенов × 2` ставить смысла нет. |
| `-v`, `--verbose` | выкл. | Debug-лог: каждый HTTP-запрос и каждый 429 с длительностью паузы. |

### Переменные окружения

| Переменная | Описание |
|---|---|
| `TRACKER_ORG_ID` | ID организации Яндекс 360 (уходит в заголовок `X-Org-ID`). Где взять: Трекер → «Администрирование» → «Организации» → «идентификатор». |
| `TRACKER_CLOUD_ORG_ID` | ID организации Yandex Cloud (`X-Cloud-Org-ID`). Нужна одна из двух переменных; если заданы обе, используется эта. |
| `TRACKER_TOKENS` | Пул токенов через запятую или перевод строки. |
| `TRACKER_TOKEN` | Один токен. Используется, только если не заданы ни `TRACKER_TOKENS`, ни `--tokens-file`. |
| `TRACKER_AUTH` | Схема авторизации по умолчанию: `OAuth` (по умолчанию) или `Bearer` для IAM-токенов. Схему можно указать и у конкретного токена: `Bearer t1.xxx`. |
| `TRACKER_RPS` | Значение `--rps` по умолчанию. |
| `TRACKER_API` | Базовый URL API, по умолчанию `https://api.tracker.yandex.net/v3`. Нужен только для тестов. |

### Как подобрать `--rps` и `--workers`

Точные лимиты API Трекера не опубликованы. На практике лимит, судя по всему, общий для аккаунта:
если аккаунт параллельно используется ещё где-то (интеграции, миграции), бекап делит лимит
с ними, поэтому для пула лучше брать токены разных аккаунтов. Ответ 429 у Трекера приходит без
`Retry-After` и `X-RateLimit-*`, так что паузы скрипт подбирает сам.

Начните с `--rps 1`–`2` и посмотрите на последнюю строку лога: для каждого токена там число
запросов и число 429. Если 429 мало — `--rps` можно поднимать; если 429 сопоставимо с числом
запросов — снижать или добавлять токены других аккаунтов.

Порядок числа запросов:

- на задачу — от 4 до 6: связи и список вложений по одному, комментарии и история — по одному,
  если API присылает заголовок `Link`, иначе по два (последний запрос получает пустую страницу);
  плюс по одному на каждое вложение и ещё по одному на каждые 100 комментариев или записей истории;
- на очередь — 2 (настройки и локальные поля) + поиск: 1 запрос на каждые 1000 задач и ещё один,
  завершающий;
- на прогон — 6 (справочники) и постраничный список очередей, если не задан `--queues`.

Для оценки сверху берите 6 запросов на задачу без вложений.

### Примеры

```bash
# пробный прогон: по 3 свежие задачи из двух очередей, с подробным логом
tracker_backup.py --out /tmp/test --queues OPS,BILLING --limit 3 --rps 1 -v

# ежедневный инкрементальный бекап всех очередей пулом токенов из файла
tracker_backup.py --out /backup/tracker --tokens-file /etc/tracker-backup.tokens --rps 2

# перевыгрузить одну очередь целиком, без вложений
tracker_backup.py --out /backup/tracker --queues OPS --full --no-files
```

## Пул токенов и rate limit

- Каждый запрос получает токен, который освободится раньше остальных. Для каждого токена
  соблюдается свой интервал `1/rps`, так что суммарная скорость ≈ `rps × число токенов`.
- На `429` токен уходит на паузу: `Retry-After` → `X-RateLimit-Reset` → экспоненциальный backoff
  с джиттером (до 60 с). Запрос сразу повторяется другим свободным токеном.
- При `X-RateLimit-Remaining: 0` токен заранее ставится на паузу до `X-RateLimit-Reset`.
- Токен, получивший `401`, исключается из пула. Если отозваны все токены, бекап останавливается.
- `5xx` и сетевые ошибки повторяются с backoff.
- Очередь обрабатывается в два этапа: сначала scroll-поиск быстро проходит все задачи и сохраняет
  `issue.json`, потом комментарии, история, связи и вложения качаются параллельно. Так scroll-контекст
  не истекает, пока идёт медленная выгрузка.
- Scroll ведётся одним токеном. Продолжения scroll не повторяются на таймаутах и 5xx (можно молча
  пропустить страницу), вместо этого поиск начинается заново — до 3 раз. Так же — если токен scroll отозван.
- Пауза токена ограничена 5 минутами, что бы ни прислал сервер; `X-RateLimit-Reset` понимается
  в секундах, unix-времени в секундах или миллисекундах.

Токены должны принадлежать пользователям (лучше роботам) с одинаковым доступом к очередям, иначе
задача, найденная одним токеном, может вернуть 403 на другом.

В конце прогона в лог выводится статистика по токенам: число запросов, 429 и отозван ли токен.

## Инкрементальность

`state.json` хранит для каждой очереди время последнего успешного прогона (минус 5 минут перекрытия).
Следующий запуск берёт только задачи с `updated >=` этого времени. Если в очереди были ошибки, время
не сдвигается и при следующем запуске задачи выгрузятся повторно.

Если поиск по очереди не нашёл ни одной задачи, время тоже не сдвигается. Трекер может временно
отдавать пустой результат — например, пока токену не выдан доступ к очереди, — и сдвинутая отметка
навсегда отрезала бы от бекапа все старые задачи. Для очереди без отметки (и при `--full`) в лог
пишется предупреждение: проверьте, что у токенов есть доступ к ней. Для очереди с отметкой —
информационная строка «изменений с … нет».

Ошибка при выгрузке настроек очереди (`queue.json`, `localFields.json`) тоже считается ошибкой
очереди и не даёт сдвинуть отметку: например, 403 на настройках обычно значит, что токену не хватает
прав, и поиск мог вернуть лишь часть задач.

`--full` выгружает выбранные очереди целиком, но не стирает отметки остальных очередей в `state.json`.

Все ошибки за прогон (задачи, поиск, метаданные) пишутся в `errors.json`, в том числе при аварийной
остановке. Код выхода: 0 — без ошибок, 1 — есть ошибки, 2 — остановка (все токены отозваны или не
удалось получить список очередей), 130 — прервано по Ctrl+C.

## Скрипт `run_backup.sh`

Обёртка для бекапа очередей `HRTECH`, `PRODUCTIV` и `HROPS` (список задан в начале скрипта).
Переменные окружения берутся из `tracker-backup.env`, токены — из `tracker-backup.tokens`; оба
файла лежат рядом со скриптом и в git не попадают.

```bash
cp tracker-backup.env.example tracker-backup.env        # заполнить TRACKER_ORG_ID и т.д.
cp tracker-backup.tokens.example tracker-backup.tokens  # по токену в строке
chmod 600 tracker-backup.tokens

./run_backup.sh                  # инкрементальный бекап
./run_backup.sh --limit 3 -v     # пробный прогон
./run_backup.sh --full           # любые аргументы передаются tracker_backup.py
```

- Каталог бекапа — `TRACKER_BACKUP_OUT` из `tracker-backup.env`, по умолчанию `./backup`.
- Пути можно переопределить переменными: `ENV_FILE`, `TOKENS_FILE`, `PYTHON` (по умолчанию
  `.venv/bin/python`).
- Если `flock` доступен (Linux), второй запуск в тот же каталог, пока идёт первый, просто выходит
  с кодом 0. Блокировка — файл `.lock` в каталоге бекапа.
- Если файл токенов доступен на чтение всем пользователям, скрипт предупредит об этом.
- Коды выхода — те же, что у `tracker_backup.py`; 2 — ещё и при отсутствии env-файла, файла токенов
  или venv.

Для cron:

```cron
30 3 * * * /opt/tracker-backup/run_backup.sh >> /var/log/tracker-backup.log 2>&1
```

## Ежедневный запуск по cron

Cron запускает команды с почти пустым окружением, поэтому переменные лучше вынести в отдельный файл,
а токены — в `--tokens-file`. Оба файла должны быть доступны только владельцу (`chmod 600`).

```bash
# /etc/tracker-backup.env
TRACKER_ORG_ID=1234567
TRACKER_RPS=5
```

```bash
# /etc/tracker-backup.tokens — по токену в строке
y0_aaa
y0_bbb
```

`crontab -e` (пример: каждый день в 03:30, проект в `/opt/tracker-backup`):

```cron
30 3 * * * cd /opt/tracker-backup && set -a && . /etc/tracker-backup.env && set +a && flock -n /tmp/tracker-backup.lock .venv/bin/python tracker_backup.py --out /backup/tracker --tokens-file /etc/tracker-backup.tokens >> /var/log/tracker-backup.log 2>&1
```

- `set -a` + `.` экспортирует все переменные из env-файла в окружение скрипта.
- `flock -n` не даёт запустить второй бекап, пока не закончился предыдущий: первый полный прогон
  может идти дольше суток. `flock` есть в Linux (util-linux), в macOS его нужно ставить отдельно
  (`brew install flock`).
- Лог дописывается в `/var/log/tracker-backup.log` — у пользователя cron должны быть права на запись,
  ротацию настройте через `logrotate`.
- Код выхода 1 или 2 означает ошибки (см. «Инкрементальность»). Скрипт пишет лог в stderr при каждом
  прогоне, поэтому для алертов проверяйте непустой `errors.json` или свежесть `state.json` мониторингом.

## Запуск в Docker

```bash
docker build -t tracker-backup .
```

Бекап пишется в `/backup` внутри контейнера, токены передаются файлом только для чтения,
остальные переменные — через `--env-file` (формат тот же, что у `/etc/tracker-backup.env` выше):

```bash
docker run --rm \
  --env-file /etc/tracker-backup.env \
  -v /etc/tracker-backup.tokens:/run/secrets/tokens:ro \
  -v /backup/tracker:/backup \
  tracker-backup --out /backup --tokens-file /run/secrets/tokens
```

Аргументы после имени образа передаются скрипту как есть (`--queues`, `--full`, `--no-files`, `-v` …).

- Процесс в контейнере работает от пользователя с UID 10001: каталог бекапа на хосте должен быть
  доступен ему на запись (`chown 10001 /backup/tracker`), а файл токенов — на чтение.
- `docker stop` останавливает бекап корректно: скрипт обрабатывает SIGTERM так же, как Ctrl+C —
  пишет `errors.json`, не сдвигает `state.json` для прерванной очереди и выходит с кодом 130.
  По умолчанию Docker ждёт 10 секунд; если идёт загрузка крупных вложений, увеличьте `docker stop -t`.
- Время в логах — UTC; для местного времени добавьте `-e TZ=Europe/Moscow`.

Ежедневный запуск через cron на хосте:

```cron
30 3 * * * flock -n /tmp/tracker-backup.lock docker run --rm --env-file /etc/tracker-backup.env -v /etc/tracker-backup.tokens:/run/secrets/tokens:ro -v /backup/tracker:/backup tracker-backup --out /backup --tokens-file /run/secrets/tokens >> /var/log/tracker-backup.log 2>&1
```
